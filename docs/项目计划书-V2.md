## 1 引言

### 1.1 标识

- 项目名称：观澜视频平台
- 项目标识号：VIDEO-PLATFORM-2026
- 文档名称：项目计划书 V2

- 项目形态：Web 端在线视频与直播网站

### 1.2 项目概述

观澜视频平台面向游客、普通用户、内容创作者与平台管理员，提供视频消费、搜索推荐、投稿审核、评论弹幕、关注订阅、直播互动、录播回看、用户中心和管理后台等能力。项目采用前后端分离架构，以 Web 端作为首版唯一交付终端，强调“内容分发 + 创作管理 + 平台治理”的完整闭环。

截至 2026 年 4 月中旬，项目已从“立项与方案阶段”进入“功能整合与验收准备阶段”。相比 V1，V2 不再只描述目标蓝图，而是以当前仓库实现和实际联调结果为基线，重新规划后续迭代重点、资源分配和验收节奏。

### 1.3 文档目的

本文档用于在当前开发进度基础上，重新明确：

- 当前系统已经完成的范围与能力边界
- 距离课程验收仍需补齐的关键工作
- 接下来 2 至 4 周的开发、测试、文档与演示安排
- 团队协作、版本控制、环境准备与风险控制策略

V2 将作为后续编码、联调、测试、部署和答辩准备的统一执行基线。

### 1.4 V2 基线说明

本次 V2 计划基于以下事实形成：

- 前端已形成主站、登录注册、用户中心、审核后台、通知中心、搜索页、视频详情页、直播页等主要页面骨架与核心交互。
- 后端已落地认证、视频、搜索、互动、关注、通知、用户中心、审核、直播、推荐画像等主要业务模块。
- 数据库与演示数据已完成基础建模与初始化脚本，支持演示账号、演示视频和审核状态流转。
- 推荐、搜索、投稿、审核、通知、用户主页、个人资料等链路已经具备可运行基础。
- 部分能力仍处于“可演示但未完全收口”状态，尤其是直播闭环、礼物币、治理增强、测试覆盖和部署文档。

## 3 项目现状总览

### 3.1 已完成的阶段性成果

当前项目已经完成或基本完成以下内容：

- 前后端工程骨架、路由、状态管理、统一 HTTP 封装和基础样式体系
- 用户注册、普通用户登录、管理员密钥登录、基础鉴权与角色区分
- 首页推荐流、分类入口、搜索联想、搜索结果页和相关推荐
- 视频上传、基础媒体处理、封面抽帧、稿件保存、提交审核、审核记录查看
- 用户稿件编辑、待审撤回、已发布内容回退草稿后再编辑并重新提交审核
- 评论、回复、点赞、收藏、关注、通知中心和未读数同步
- 用户主页、个人资料编辑、昵称编辑、头像与简介维护
- 管理后台的视频审核、文本审核、举报处理、审核记录保留与复审能力
- 直播页和相关接口骨架，具备后续真实链路接入基础

### 3.2 当前仍未完全收口的重点

- 直播链路还需要形成稳定可验收的“推流 - 观看 - 聊天/弹幕 - 录播”闭环
- 礼物币与直播礼物仍处于规划或演示态，未形成完整业务流程
- 管理后台治理能力仍偏首版，需要补充筛选、备注、回溯和更多审核对象
- 测试用例、测试报告、部署文档、用户手册等过程交付物尚需完善
- 远程服务器部署与本地开发环境仍存在双环境差异，需要统一演示口径

### 3.3 当前环境基线

- 前端：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus
- 后端：NestJS 风格 TypeScript 服务
- 数据层：Prisma + MySQL
- 媒体链路：MinIO + FFmpeg
- 直播链路：SRS
- 推荐增强：规则推荐 + 用户画像 + 搜索个性化重排
- 运行方式：本地开发环境与远程云主机环境并存

V2 的核心目标不是再扩张大量新范围，而是让现有范围达到“可验收、可演示、可说明”的状态：

- 保证视频消费、投稿、审核、通知、用户中心这几条主流程稳定可演示
- 保证已上线功能的文档、接口、数据库和界面表达保持一致
- 聚焦直播闭环、治理增强和测试验收，减少无边界扩展
- 将当前功能从“能跑通”提升到“能答辩、能复盘、能交付”

## 6 V2 开发策略

### 6.1 总体策略

V2 阶段采用“收敛优先、闭环优先、验收优先”的开发策略：

- 优先收敛已有能力，不盲目新增与验收无关的大功能
- 优先完成可从前端到后端再到数据层完整跑通的闭环
- 优先解决答辩中最容易暴露的问题：链路不稳定、文档与代码脱节、环境不一致

### 6.2 技术策略

- 前端继续沿用 Vue 3 + TypeScript 单页应用模式
- 后端继续采用单体模块化结构，避免在收尾阶段引入微服务复杂度
- 媒体与直播相关能力维持 MinIO + FFmpeg + SRS 方案
- 推荐与搜索继续使用规则和画像增强策略，不引入额外训练系统
- 统一保持接口前缀、字段命名、状态机和文档描述一致

### 6.3 版本策略

- `V1` 保留为项目启动与初版规划基线
- `V2` 作为当前开发和验收准备基线
- 后续若进入答辩前封板，可再输出 `V3` 作为最终交付版

## 7 详细活动计划

### 7.1 功能收敛活动

- 逐模块盘点“已完成、可演示、待补齐、暂缓”的状态
- 对视频、审核、通知、用户中心、直播等主流程做闭环自检
- 对状态流转进行统一梳理，避免前端允许但后端拒绝的情况

### 7.2 联调与修复活动

- 以前后端接口为边界，逐条核对请求参数、返回结构和状态码
- 修复已知体验缺陷，如状态切换后界面未及时更新、资料修改未持久化等
- 校对后台审核记录、用户稿件队列、通知计数等需要即时同步的状态

### 7.3 测试活动

- 设计围绕核心流程的手工回归用例
- 补充上传、审核、通知、互动、资料编辑和直播的冒烟测试
- 建立一套适用于答辩演示的标准操作脚本和预置数据

### 7.4 文档活动

- 补充和更新计划书、需求、设计、API、数据库和部署文档
- 将当前代码实现中的关键变化同步写入文档
- 补充答辩讲稿、演示步骤、角色账号、环境说明和异常预案

### 7.5 环境与部署活动

- 明确本地环境与云端环境分别承担的职责
- 清理不再需要的本地服务，减少环境噪音
- 固化远程数据库、对象存储和部署配置说明

## 9 组织与分工建议

### 9.1 分工原则

- 每位成员至少负责一条可完整描述的核心链路
- 复杂链路如直播、审核、推荐必须指定明确主责人
- 文档工作与实现工作同步进行，不允许最后集中补写

### 9.2 建议职责划分

| 角色方向 | 重点职责 |
| --- | --- |
| 前端主责 | 主站、搜索、通知、用户中心、后台页面联调 |
| 后端主责 | 认证、视频、审核、通知、用户资料接口稳定性 |
| 实时媒体主责 | SRS、录播、直播间状态、推拉流联调 |
| 数据与推荐主责 | 数据初始化、推荐画像、搜索排序和演示数据 |
| 测试与文档主责 | 测试用例、报告、部署文档、答辩材料整合 |

## 10 配置与版本管理

- 使用 Git 进行版本管理，优先采用功能分支开发
- 提交信息保持语义化，如 `feat`、`fix`、`docs`、`refactor`
- 环境变量模板与真实配置分离管理，严禁公开敏感信息
- 本地辅助文件、记忆文件、截图和临时产物不得进入最终提交

## 11 质量目标

### 11.1 功能质量

- 关键链路可稳定跑通：注册登录、投稿审核、通知、资料编辑、审核后台
- 直播链路至少达到小规模演示稳定
- 后台治理操作可解释、可回溯、可复演

### 11.2 文档质量

- 文档中的接口、字段、状态与代码实现一致
- 文档内容真实反映当前系统，不做未实现能力的虚假承诺
- 验收材料与演示脚本统一口径

### 11.3 演示质量

- 演示环境在答辩前完成一次全流程彩排
- 默认账号、测试视频、审核记录、通知数据保持可复现
- 对直播、网络、外部服务异常准备降级展示方案

## 12 风险管理

| 风险 | 当前表现 | 应对措施 |
| --- | --- | --- |
| 直播链路风险 | 直播能力已具基础但仍可能不稳定 | 先打通最小演示闭环，准备录播兜底方案 |
| 环境不一致风险 | 本地与云端服务混用，配置口径易混乱 | 固化 `.env` 说明与演示环境清单 |
| 功能回归风险 | 近期连续修改较多，主流程易互相影响 | 形成固定回归清单，功能改动后立即冒烟 |
| 文档滞后风险 | 功能已迭代多轮，V1 已不完全匹配现状 | 以 V2 为新基线，同步更新其余文档 |
| 验收表达风险 | 功能有实现但可能缺少清晰叙述 | 提前整理“需求 - 实现 - 演示 - 文档”映射表 |
