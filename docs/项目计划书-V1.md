# 项目计划书 V1

## 1 引言

### 1.1 标识

- 项目名称：观澜视频平台（暂定名）
- 项目标识号：VIDEO-PLATFORM-2026
- 文档名称：项目计划书 V1
- 版本号：v1.0
- 编写日期：2026-04-06
- 项目性质：软件工程基础 2026 春大作业
- 项目形态：Web 端在线视频与直播网站

### 1.2 项目概述

观澜视频平台面向视频观看者、平台用户与平台管理员，提供短视频、中视频、长视频与直播内容的统一消费入口，支持视频推荐与搜索、内容发布与审核、弹幕评论、关注订阅、真实推流直播、用户中心与审核后台等功能。项目整体风格以 B 站式社区主站为主体，首页入口借鉴抖音式推荐流，强调内容消费、创作管理、直播互动与社区治理的闭环。

本项目按照课程大作业要求组织开发，除可运行系统外，还需同步完成计划书、需求规格说明书、概要设计说明书、详细设计说明书、测试报告、部署文档与用户手册等过程与验收文档。

### 1.3 文档目的

本文档用于明确项目范围、开发策略、里程碑、资源分配、质量要求与风险对策，作为项目启动阶段的执行基线。V1 版本用于甲乙双方协商与项目组内部对齐，后续会随着需求冻结和架构细化持续更新。

### 1.4 基线

当前计划书基于以下已确认事项形成：

- 选题：第四部分“在线视频与直播网站”
- 终端：首版仅 Web 端
- 技术方向：Node.js 技术栈
- 产品定位：B 站式主站 + 抖音式推荐入口 + 真实推流直播
- 推荐方式：规则版推荐
- 审核策略：先审后发
- 平台治理：必须包含管理审核后台
- AI 亮点：必须包含 Agent 模块

## 4 项目范围与工作概述

### 4.1 目标用户

- 游客：浏览与播放公开视频和直播内容
- 用户：点赞、收藏、评论、回复、发送视频弹幕、关注用户
- 用户：观看内容、互动、投稿视频、提交审核、管理作品、开播、查看数据与违规提醒
- 管理员：审核内容、处理举报、管理分类与推荐位、查看运营数据、使用 Agent 审核辅助

### 4.2 核心需求清单

| 编号 | 核心需求 | 说明 |
| --- | --- | --- |
| CR-01 | 内容消费与分发 | 首页推荐、频道分区、全局搜索、视频详情、相关推荐 |
| CR-02 | 内容发布与审核 | 投稿、编辑、媒体处理、提交审核、审核通过后发布 |
| CR-03 | 社区互动 | 点赞、收藏、评论、二级回复、视频弹幕、通知 |
| CR-04 | 关注订阅 | 关注/取关、订阅流、用户主页、粉丝关系 |
| CR-05 | 直播互动 | 真实推流、直播间播放、直播聊天、直播弹幕、录播回看 |
| CR-06 | 用户中心 | 作品管理、直播管理、数据概览、粉丝趋势、违规提醒 |
| CR-07 | 平台治理与 Agent | 审核后台、举报处理、敏感词过滤、违规处置、AI 审核辅助 |

### 4.3 首版功能边界

#### 必做范围

- 短/中/长视频统一发布与播放
- 先审后发的审核流
- 首页推荐流与全局搜索
- 评论与二级回复
- 视频弹幕与直播弹幕分离实现
- 关注与订阅流
- 真实推流开播与直播观看
- 直播录播回看
- 用户中心与管理员后台
- 每日登录领取礼物币，礼物币可用于直播礼物兑换与发送
- Agent 审核辅助

#### 简化范围

- 推荐算法采用规则版，不引入复杂机器学习训练系统
- 虚拟礼物仅做平台内模拟，不接入真实支付
- 录播回看仅做基础回看，不做剪辑与章节管理
- 搜索首版采用统一检索接口与分 Tab 展示，不引入复杂搜索引擎集群

#### 暂不纳入首版

- 原生移动端 App
- 实时连麦、多人 PK、直播切片
- 完整商业化结算系统
- 大规模分布式推荐召回系统

### 4.4 内容分区

首版固定一级分区：

- 推荐
- 娱乐
- 学习
- 游戏
- 科技
- 直播

### 4.5 关键约束

- 开发周期受课程节点约束，需要按周完成文档与系统演进
- 项目必须能够在本地或指定服务器环境中稳定演示

## 5 开发策略与总体计划

### 5.1 开发方法

项目采用“迭代增量 + 轻量 Scrum”方式推进，以一周为一个小迭代。每轮迭代包含需求确认、任务拆分、开发联调、回顾修正四个动作。

### 5.2 技术路线

- 前端：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus
- 后端：NestJS + TypeScript
- 数据库：MySQL 8
- 缓存：Redis
- 文件存储：MinIO
- 媒体处理：FFmpeg
- 直播服务：SRS
- 实时通信：WebSocket
- 部署：Docker Compose + Nginx
- Agent：基于可配置大模型接口的审核辅助模块

### 5.3 系统架构策略

- 采用前后端分离架构
- 后端首版采用单体模块化设计，而非微服务
- 直播推流与播放依赖独立流媒体服务 SRS
- 视频上传后进入媒体处理流程，处理完成后再进入审核流
- 审核通过的内容才进入推荐、搜索与公开播放范围

### 5.4 阶段划分

#### 阶段一：需求与规划

- 完成项目范围冻结
- 输出计划书 V1
- 确认核心需求、角色模型、模块划分

#### 阶段二：需求分析

- 输出需求规格说明书
- 完成竞品调研、业务流程、用例建模、需求编号体系
- 输出低保真页面草图与核心状态流转

#### 阶段三：系统设计

- 输出概要设计说明书与数据库设计
- 明确接口规范、数据模型、系统部署架构
- 设计直播链路、审核链路与 Agent 接入点

#### 阶段四：详细设计与编码

- 完成前后端工程骨架
- 实现核心主流程
- 建立测试环境与初始数据

#### 阶段五：测试与验收准备

- 完成功能测试、联调测试、性能冒烟测试
- 输出测试报告、部署文档、用户手册
- 录制演示视频与制作答辩 PPT

## 6 详细活动计划

### 6.1 需求分析活动

- 提炼核心需求与验收边界
- 识别角色、状态、业务对象
- 明确游客与登录用户权限差异
- 确认内容分区、搜索范围、互动策略、礼物币机制、直播回看要求

### 6.2 设计活动

- 设计前端信息架构与页面路由
- 设计后端模块边界与接口规范
- 设计数据库核心实体关系
- 设计媒体处理、审核状态机、直播状态机
- 设计 Agent 审核辅助交互位置和输出结构

### 6.3 编码活动

- 建立 `frontend`、`backend`、`deploy`、`docs` 目录
- 搭建 NestJS 后端基础设施：鉴权、配置、日志、统一返回体、错误处理
- 搭建 Vue 前端基础设施：路由、状态管理、主题样式、HTTP 封装
- 接入 MinIO、FFmpeg、SRS、Redis
- 逐步完成视频、互动、直播、审核、用户中心、Agent 模块

### 6.4 测试活动

- 单元测试：核心服务逻辑与工具函数
- 接口测试：鉴权、内容、互动、直播、审核接口
- 联调测试：上传至审核发布、直播开播至回看、评论弹幕链路
- 演示冒烟：游客/用户端、用户中心、管理员端完整演练

### 6.5 文档活动

- 过程文档与实现同步演进
- 每轮迭代后更新需求变更、接口变更与数据库变更
- 所有图片、流程图、原型图放入仓库相对路径，避免本地绝对路径失效

### 6.6 配置与版本管理

- 使用 Git 进行版本管理
- 采用功能分支开发与合并请求审查
- 约定提交信息前缀：`docs`、`feat`、`fix`、`refactor`、`test`、`chore`
- 建立环境变量模板文件，严禁提交真实密钥

### 6.7 质量保证

- 代码规范统一使用 ESLint + Prettier
- 关键接口与状态机逻辑必须经过双人复核
- 文档中出现的功能、表结构、接口命名须与代码实现一致
- 所有演示账号与测试数据在验收前统一检查

## 10 项目估算

### 10.1 工作量估算

- 需求与文档：20%
- 前端页面与交互：25%
- 后端业务接口：25%
- 直播与媒体处理：15%

### 10.2 复杂度评估

项目的主要复杂度集中在以下部分：

- 真实推流直播链路
- 视频媒体处理与审核状态流转
- 视频弹幕与直播弹幕的分离实现
- Agent 审核辅助与人工审核协同
- 用户中心与管理员后台的多角色联动

## 11 风险管理

| 风险 | 描述 | 应对措施 |
| --- | --- | --- |
| 技术风险 | 团队对 SRS、FFmpeg、NestJS 不熟 | 提前预研，先打通最小链路 |
| 工期风险 | 文档与开发不同步，后期集中补写 | 每阶段同步维护文档 |
| 联调风险 | 前后端接口定义频繁变动 | 提前冻结接口规范与返回格式 |
| 演示风险 | 直播、审核、Agent 演示链路不稳定 | 建立演示专用环境与脚本 |
| 性能风险 | 视频上传、推流、WebSocket 消息处理不稳 | 做小并发冒烟和压测 |
| 合规风险 | 内容审核逻辑过弱，无法体现治理能力 | 强化审核后台、举报与 Agent 风险提示 |
