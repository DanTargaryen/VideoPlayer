## 可直接发送的版本

老师/助教您好，我们是“观澜视频平台”小组。根据《软件工程基础实践》任务书，我们已在现有项目基础上整理业务场景，计划将原 CR-01 至 CR-07 收敛为以下 6 个端到端用例：

1. UC01 账户访问与资料维护；
2. UC02 视频发现、播放与观看记录；
3. UC03 投稿、媒体处理、审核与发布；
4. UC04 视频互动、关注与通知；
5. UC05 直播、互动、礼物与录播回看；
6. UC06 举报、审核与治理处置。

每个用例都会写参与者、触发条件、前置条件、主成功流程、异常流程和可验证结果，并建立 REQ/UC/系统级图/组件级图/对象级图/单元测试/API 测试/E2E 测试的追溯关系。

想请您确认以下问题：

1. 将推荐/搜索/播放合并为 UC02、将点赞/收藏/评论/弹幕/关注/通知合并为 UC04，是否符合“一个明确业务目标的完整流程”的认定？
2. AI 视频问答、全局助手、评论机器人、动态广场、私信和连续签到，能否作为上述用例的备选能力或不纳入本次独立验收用例，而不是分别单列？
3. 直播功能当前存在部分状态内存化问题。若我们在第一阶段修复并在第二阶段提取为独立服务，UC05 是否按完整用例计入？如果无法在 D1 稳定验证，是否允许在确认记录中缩减范围？
4. 微服务计划暂定为 identity-community、content-media、live-reward、governance-ai 四个业务服务；API 网关、前端、数据库不计数。该划分是否可接受？
5. CI/CD 计划使用 GitHub Actions，Kubernetes 使用 Docker Desktop + kind/k3d（或远端 k3s），同一 MySQL 容器内使用多个 Schema、每服务独立账号且禁止跨服务直接查询。该工具和数据隔离方案是否可接受？

我们会以您的回复为最终范围依据，并把确认记录放入项目管理证据中。谢谢！
