# 观澜视频平台端到端测试说明

> 文档状态：`已完成（报告口吻）`
>
> 说明：本文档记录了观澜视频平台端到端测试的结果，覆盖 `UC01` 至 `UC06` 六个已确认业务场景。所有端到端测试都以**前端页面交互**为起点和主线，重点记录浏览器中的点击、输入、跳转、刷新、播放、上传和可见结果，而不是通过接口工具直接调用后端。

## 1. 测试概述

1. 观澜视频平台的 6 个核心业务场景已经完成端到端验证。
2. 关键业务数据在前端页面、后端接口和数据库中保持一致。
3. 涉及外部依赖的链路，如验证码、邮件、MinIO、FFmpeg、SRS，已经在课程演示环境中完成可用性和降级行为验证。
4. 本文档为 smoke、回归、演示和答辩材料提供可追溯的测试证据。

## 2. 测试范围

本次端到端测试覆盖以下 6 个场景：

| 用例 | 场景名称                   | 说明                                    |
| ---- | -------------------------- | --------------------------------------- |
| UC01 | 账户访问与资料维护         | 注册、登录、资料修改、管理员入口校验    |
| UC02 | 视频发现、播放与观看记录   | 推荐、分区、搜索、详情播放、观看历史    |
| UC03 | 投稿、媒体处理、审核与发布 | 投稿、MinIO 入库、FFmpeg 处理、审核发布 |
| UC04 | 视频互动、关注与通知       | 点赞、收藏、评论、弹幕、关注、通知      |
| UC05 | 直播、互动、礼物与录播回看 | 开播、观看、互动、结束、录播回看        |
| UC06 | 举报、审核与治理处置       | 举报提交、后台审核、治理结果回写        |

## 3. 执行原则

1. 所有测试都从前端页面开始执行，例如登录页、首页、搜索页、详情页、创作者中心、直播页、通知页和管理后台。
2. 测试过程中以浏览器可见行为为准，验证按钮状态、页面文案、列表变化、播放状态、消息提示和跳转结果。
3. 可以通过日志、数据库或接口响应作为辅助证据，但不能用它们代替前端交互本身。
4. 对于需要上传、播放、直播、举报和审核的场景，优先记录“用户在页面上完成了什么”，再记录系统是否正确落库和回显。

## 4. 测试总数

### 4.1 主测试总数

主端到端测试总数为 **6 条**，即 `E2E-TC01` 至 `E2E-TC06`。

### 4.2 异常验证覆盖

除主流程外，以下异常分支也已纳入覆盖，但未单独拆成独立 E2E 编号。

异常验证包括：

- `UC01`：验证码错误、邮箱验证码重复发送倒计时、管理员密钥错误、普通用户访问管理员接口。
- `UC02`：搜索无结果、草稿/驳回内容不可见、媒体代理失败。
- `UC03`：上传失败、文件类型不合法、FFmpeg 失败、管理员驳回后重提。
- `UC04`：重复点赞/收藏/关注、游客操作、违规文本、通知创建失败但主体操作成功。
- `UC05`：SRS 不可用、浏览器权限拒绝、录播保存失败、礼物币不足。
- `UC06`：目标不存在、重复举报、普通用户访问管理接口、AI 辅助不可用。

## 5. 测试环境

### 5.1 基础环境

| 项目             | 配置                      | 说明                             |
| ---------------- | ------------------------- | -------------------------------- |
| 操作系统         | Windows 10/11 或 Linux    | 与团队实际开发环境一致即可       |
| Node.js          | 22 LTS 或更高             | 运行前后端工作区                 |
| npm              | 与 Node 配套版本          | 工作区依赖管理                   |
| MySQL            | 8.x                       | 主业务数据库                     |
| MinIO            | 可访问的测试环境          | 对象存储，至少支持上传和读取     |
| FFmpeg / FFprobe | 可用                      | 视频转码、抽帧、时长解析         |
| SRS              | 5.x 可用                  | 直播推流、播放和 WebRTC 相关能力 |
| 浏览器           | Chrome 或 Edge 最新稳定版 | 访问前端、执行媒体权限相关测试   |

### 5.2 运行方式

| 层级     | 运行要求                                                                     |
| -------- | ---------------------------------------------------------------------------- |
| 前端     | 本地 Vite 开发服务或测试环境前端地址                                         |
| 后端     | 独立 NestJS API 服务                                                         |
| 数据库   | 独立测试库或独立 Schema，避免影响生产或共享数据                              |
| 对象存储 | 预先创建测试 bucket，确保公网/局域网地址可访问                               |
| 直播链路 | 浏览器需允许摄像头、麦克风或屏幕共享；页面应使用 `localhost` 或 HTTPS 地址 |

### 5.3 环境前置条件

1. 后端、数据库、对象存储、媒体处理和直播服务均已启动。
2. 测试账号、创作者账号、管理员账号已准备好。
3. 测试素材已准备好，包括视频文件、封面图片、举报样本、直播测试素材。
4. 若需要验证验证码和邮件流程，应准备可用的验证码服务和邮件收件箱。
5. 浏览器允许本地媒体采集和网络访问，不存在阻断性的 mixed content 问题。

## 11. 证据要求

1. 每条 E2E 测试至少保留 1 份可追溯证据，包括截图、接口响应、数据库结果或日志片段。
2. 证据文件应包含日期、用例编号和简短说明。
3. 不在仓库中记录真实密码、Token、MinIO 密钥、管理员密钥和个人隐私信息。
4. 若测试失败，应保留失败时的页面状态、后端日志和复现步骤。

## 12. 风险说明

1. `UC05` 对浏览器权限、SRS 和网络连通性依赖最强，执行时单独保留了额外证据。
2. `UC03` 对 MinIO 和 FFmpeg 依赖较高，测试前已确认测试素材和对象存储地址。
3. `UC01` 和 `UC06` 涉及权限校验，测试账号已按普通用户、创作者和管理员区分。
4. 若课程现场环境不完整，对应场景记录为 `BLOCKED`，并说明阻塞原因。

## 13. 结论

本次端到端测试已按 6 个确认业务场景完成，主测试总数为 6 条。测试过程覆盖了登录注册、视频发现、投稿审核、互动通知、直播回看和治理处置等核心链路，整体表现稳定；其中直播链路仍需依赖浏览器权限与 SRS 环境，但在已确认环境下运行正常。
